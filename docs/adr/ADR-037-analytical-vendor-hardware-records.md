# ADR-037 — Vendor hardware records for devices this project has never run on

**Status:** Accepted
**Date:** 2026-08-20

## Context

The user asked, explicitly aware of the framing, for a hardware record and
roofline analysis of a real GPU (NVIDIA H100 SXM5) that this project has never
had access to — "make sure to write as an important line that this is purely
theoretical." This is a legitimate and useful thing to build (TDD §9, §33), but
it sits directly next to the project's central discipline: never fabricate a
number, never let a `VENDOR_REPORTED` figure be mistaken for `MEASURED`.

Two things needed deciding: how to source real numbers honestly when the
project's tooling could not parse NVIDIA's own datasheet PDFs, and how to make
"this device has never been run on" impossible to miss.

## Decisions

**1. Sourcing: cross-check secondary transcriptions, don't invent from memory.**
NVIDIA's own PDF whitepaper/datasheet could not be parsed by this session's
tooling (binary/compressed PDF streams; no `poppler-utils`, no root to install
it — same limitation as ADR-036 elsewhere in this project). Every figure in
`hardware/gpu/nvidia-h100-sxm5-80gb.yaml` was instead cross-checked across at
least two independent secondary sources that transcribe NVIDIA's own published
numbers. Where sources agreed, confidence is `HIGH`; where only one source (or
an interpretation, such as which of two numbers is the sparse vs. dense
figure) supported a value, confidence is `MEDIUM` — and that reasoning is
written into each field's own `notes`, not left implicit.

**2. `PeakComputeValue` (ADR-036's sibling addition) enforces TDD §9.1 by
type.** Every one of the H100 record's 13 precision entries has a known peak
value, so every one is required to carry `conditions` — enforced at
validation time, not by review.

**3. The "purely theoretical" warning is structural, not a comment that can
be deleted by accident.** It appears in four independent places: the hardware
YAML's file header, the `measurement_host_qualified` field (`false`, with a
note distinguishing this from ADR-032's case — a real disqualified host vs. a
device that is not present in any form), the roofline CLI command's runtime
banner (printed every invocation, not opt-in), and the generated report's
opening blockquote. Losing any one of the four still leaves three others.

**4. `roofline.py` cannot produce a `MEASURED` value by construction.** It has
no execution path — no kernel launch, no timer, nothing that could run on
hardware even if hardware existed. Its only output type is `DerivedMetric`,
which is itself validator-enforced to carry `provenance=DERIVED` and never
anything else (see `phoenix/provenance.py`). A roofline point traces to
`VENDOR_REPORTED` inputs via `DerivedMetric.inputs`, exactly as Tier 3 requires.

**5. The report is generated by a script, never hand-typed.** Same discipline
as `results/figures/`, applied to a theoretical artefact: `roofline_report.py`
computes every table cell; nothing in `docs/analysis/nvidia-h100-sxm5-roofline.md`
was copy-pasted from a terminal or written by hand.

## What this does NOT do

Does not add H100 as a `phoenix run`-able backend or an EXP-xxx experiment —
there is no CUDA backend and no hardware, so nothing here executes anything.
Does not place output under `results/`, which TDD §10 reserves for real
run packages; the report lives under `docs/analysis/` instead, clearly
documentation rather than data. Does not claim GPU support of any kind.

## Revisit trigger

Real H100 (or any GPU) access is acquired. At that point this record becomes
one of two things: superseded by a record built from the vendor's own
directly-parsed documentation (closing the "secondary source" caveat), or
supplemented by genuinely `MEASURED` fields (`bandwidth_attained`, power
telemetry) once EXP-002 onward actually executes.
